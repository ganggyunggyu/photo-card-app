# 클로드 보고서 — E2E(스캔→검증→트리거) 기준 소프트웨어 심층 점검

목표 플로우(릴레이 접점/ESP 펄스/로컬 Wi‑Fi HTTP/원자적 쿠폰 사용처리/단순 UI)를 그대로 따른다고 가정했을 때, **현재 레포 상태 대비 소프트웨어 쪽에서 추가로 손봐야 “현장 운영이 안 터지는” 지점**을 우선순위로 정리했다.

---

## 0) 현재 레포 기준 “이미 된 것”

- 스캔(카메라): `@zxing/browser` 기반 `src/features/coupon-scan/ui/CameraTab.tsx`
- 쿠폰 원자적 사용처리: `src/app/api/coupons/validate/route.ts`의 `findOneAndUpdate({couponNumber,isUsed:false})`
- BLE 트리거(기존): `src/features/ble-connection/hooks/useBLE.ts` → ESP32 BLE GATT(`esp32/photo_card_trigger.ino`)

즉, **BLE 기준 E2E는 이미 뚫려 있음**. 앞으로는 “운영 안정성 + HTTP 전환 + 로그/재시도/보안”이 핵심이다.

---

## 1) 1순위 리스크: HTTPS(카메라) ↔ HTTP(ESP) “혼합 콘텐츠” 문제

카메라 스캔은 브라우저에서 **Secure Context(HTTPS/localhost)**가 사실상 필수다.  
그런데 목표안처럼 탭이 ESP의 `http://<local-ip>/dispense`를 직접 호출하면:

- HTTPS 페이지 → HTTP 요청은 **Mixed Content로 차단**될 수 있음(Chrome 기본 정책).
- 설령 Mixed Content를 피하더라도, 교차 출처 요청이라 **CORS**도 추가로 풀어야 함.

### 권장 해법(현장 난이도/안정성 기준)

**A안(추천): Next API가 ESP로 프록시**
- 브라우저는 `POST /api/dispense`(same-origin, HTTPS)만 호출
- Next Route Handler가 서버에서 `http://esp.local/dispense`로 요청
- 브라우저 Mixed Content/CORS 이슈를 **원천 차단**

**B안: ESP도 HTTPS 제공**
- ESP32 TLS + 인증서 문제(신뢰 체인/셀프사인 예외 처리) 때문에 현장 난이도↑

**C안: 웹을 HTTP로 내림**
- 카메라가 안 되는 경우가 많아(secure context) 실전에서 막힘

> 결론: “로컬 Wi‑Fi HTTP”를 쓰더라도 **브라우저가 직접 ESP를 치지 말고, Next API가 대신 치는 구조**가 제일 덜 터진다.

## 2) 2순위: “쿠폰 사용 처리”와 “배출 트리거”의 원자성/재시도 설계

현재 구조는 `validate`에서 이미 `isUsed=true`로 바꾼 뒤에(성공 응답) 트리거를 날린다.  
이 경우 **하드웨어/통신 실패**가 나면 “쿠폰은 소진됐는데 배출은 안 됨” 사건이 생길 수 있다.

운영에서 이 케이스가 가장 큰 민원 포인트가 된다.

### 선택지(우선순위/복잡도별)

**옵션 1: 단순 운영(현행 유지) + 실패 로그 + 수동 대응**
- 장점: 구현 최소
- 단점: 실패 시 쿠폰 소진

**옵션 2: 2단계 상태값 도입(추천)**
- 쿠폰에 상태를 추가해 “예약→배출확정” 흐름으로 바꿈
  - 예: `redeemStatus: 'UNUSED' | 'PENDING' | 'USED'`
  - `dispensedAt`, `dispenseAttemptCount`, `lastDispenseError`
- `PENDING`에는 TTL(예: 2분)을 걸어 자동 롤백(또는 재시도 허용)

**옵션 3: 서버에서 redeem+dispense를 1 API로 묶고 결과에 따라 커밋**
- DB 업데이트와 “하드웨어 트리거”는 진짜 원자화가 불가능(외부 사이드이펙트)이라,
  - 응답 유실/중간 실패 시 **중복 배출** 또는 **미배출 소진** 둘 중 하나 리스크는 남는다.
- 그래서 보통은 “PENDING + idempotency key + 제한된 재시도”가 실전 해법.

---

## 3) 3순위: 로그(감사/운영) 없으면 현장에서 원인 추적이 안 됨

요구사항대로 “쿠폰번호, 결과, 시간, 디바이스ID”는 반드시 남기는 편이 좋다.

### 권장 로그 스키마(예시)

- `couponNumber: string`
- `kioskId: string` (브라우저 로컬에 생성/고정)
- `result: 'INVALID' | 'ALREADY_USED' | 'VALID_AND_REDEEMED' | 'ERROR'`
- `triggerTransport: 'HTTP' | 'BLE'`
- `triggerResult: 'SUCCESS' | 'FAILED' | 'SKIPPED'`
- `createdAt: Date`
- (선택) `ip`, `userAgent`, `redeemedAt`, `dispensedAt`

### TTL 인덱스

- “행사 운영 로그는 7~30일만 보관” 같은 정책이면 TTL 인덱스로 자동 정리 가능.

## 4) 4순위: FE 데이터 패칭/상태관리 “지금은 단일 파일 오케스트레이션”

현재 `src/app/page.tsx`에서 `fetch`로 직접 호출하고 상태도 로컬 `useState`로만 관리한다.

운영 안정성(재시도/중복 방지/에러 표준화)을 위해:

- TanStack Query로 `validate`를 `useMutation`으로 정리
  - `retry: 0|1`, `networkMode`, `onError`에서 UI 동작 통일
- Jotai로 “kioskId / trigger 설정(ESP 주소, 토큰) / 마지막 처리 상태”를 atom으로 분리
- 스캔 입력(카메라/USB) 이벤트가 **연속으로 들어와도 1건만 처리**하도록 “processing lock” 필요

## 5) 5순위: “인터넷 끊긴 행사장” 대비(외부 자산 의존성 제거)

현재 `src/shared/ui/StatusBadge.tsx`는 Lottie JSON을 **lottiefiles CDN에서 런타임 fetch** 한다.

- 행사장 Wi‑Fi가 “로컬만 되고 인터넷은 막힘”이면 애니메이션 로딩이 실패한다.
- UI 피드백이 깨지면 운영자가 상태를 못 본다.

권장:
- Lottie JSON을 `public/` 또는 `src/shared/assets/`에 **번들로 포함**
- 또는 `lucide-react` 같은 아이콘 + CSS 애니메이션으로 대체(더 단단함)

---

## 6) 6순위: Tailwind 클래스 유효성(특히 z-index)

현재 `src/app/page.tsx`에 `z-9999` 같은 클래스가 보이는데, Tailwind 기본 스케일에는 없어서 적용이 안 될 수 있다.

권장:
- `z-[9999]` 같은 arbitrary value 사용
- 전반적으로 `cn()` 유틸 도입 후 className 조합을 통일

## 7) 7순위: 보안(로컬이라도 “아무나 쿠폰 소진/배출” 방지)

운영 환경이 “같은 Wi‑Fi”라는 이유로 안전하지 않다.

최소 방어선(난이도 낮은 순):
- **SSID 자체를 행사 운영 전용으로 분리**(게스트/외부 접근 차단)
- Next API에 `X-KIOSK-KEY` 같은 헤더 키를 요구(키오스크 단말만 알고 있음)
- ESP `/dispense`에도 `X-ESP-KEY`(프리셰어드 키) 적용
- `/api/coupons/validate`에 간단한 rate limit(초당 N회) 또는 IP allowlist

## 7-1) 설정/시크릿 관리(운영 사고 방지)

- `scripts/seed.ts`에 **MongoDB Atlas 접속 문자열(아이디/비번 포함)**이 하드코딩되어 있다.
  - 운영/공유 레포 기준으로는 사고 포인트라, **즉시 제거**하고 `MONGODB_URI`만 강제하는 편이 안전하다.
- `.env.local`은 커밋 금지 유지(현재 가이드와 동일).

## 8) HTTP 트리거 스펙(권장) — “테스트가 쉬운 형태”

ESP(또는 Next 프록시) 기준으로 아래 형태가 제일 디버깅이 쉽다.

- `GET /health` → `{ ok: true, uptimeMs, cooldownRemainingMs }`
- `POST /dispense` → `{ ok: true }` 또는 `{ ok: false, reason: 'COOLDOWN', cooldownRemainingMs }`

추가로:
- `POST /dispense`는 **멱등 키(idempotencyKey)**를 받을 수 있으면(예: 쿠폰번호+timestamp) 중복 트리거 방지에 도움 됨

---

## 8-1) API 응답 계약(프론트 안정성)

현재 `/api/coupons/validate`는 500에서 `{ error: 'Internal server error' }`처럼 **status 필드 없이** 내려갈 수 있다.  
UI는 `status`를 전제로 렌더링하므로, 운영 안정성을 위해 아래 중 하나로 통일하는 게 좋다.

- 항상 `{ status: COUPON_STATUS.INVALID, error }` 형태로 내려서 화면이 깨지지 않게 만들기
- 또는 `COUPON_STATUS.ERROR` 같은 상태를 추가해 UI에서 명확히 처리

## 9) “다음 작업(소프트웨어)” 추천 우선순위(실행 체크리스트)

1. (필수) HTTP 전환 시 Mixed Content/CORS 대응 구조 확정(추천: Next API 프록시)
2. (필수) ESP 쿨다운 12초 + 펄스 100~300ms + 부팅 튐 방지(풀다운/초기 LOW)
3. (권장) 로그 컬렉션 + TTL 인덱스 + `kioskId` 도입
4. (권장) TanStack Query/Jotai 셋업 후 validate/trigger 흐름을 mutation 기반으로 재정리
5. (권장) Lottie 외부 fetch 제거(오프라인 대응)
6. (선택) “PENDING→USED” 상태로 재시도/미배출 소진 이슈 완화
